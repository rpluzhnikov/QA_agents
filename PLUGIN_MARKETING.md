# Kensa-QA — маркетинговый бриф

> Единый источник маркетинговой фактуры по плагину. Сводит воедино `README.md`,
> `PLUGIN_LANDING.md`, `BROWSER_AND_ROUTINES.md`, `SCHEMA-ADAPTATION-AND-BLUEPRINTS.md`,
> `engines.json` и манифест плагина.
>
> **Версия:** 0.14.0 · **Движки:** Claude Code + OpenAI Codex · **Лицензия:** MIT
> Все цифры сверены с репозиторием: **15 slash-команд · 33 навыка · 4 типа агентов · 5 источников правды**.

---

## 1. Одной строкой

**Покажи на тикет — получи чек-лист покрытия и папку готовых ручных тест-кейсов, написанных в стиле твоего проекта и готовых к коммиту.**

Kensa-QA — это не «ещё один автотест-раннер». Это **команда ручного QA** (тест-лид + инженеры + стратеги), которая живёт прямо в AI-редакторе, читает спеку из вашего трекера и **проектирует тесты** так, как это сделал бы сильный QA-инженер с сертификатом ISTQB.

Целевой формат — [Kensa](https://kensa.dev) TMS (plain markdown под `.tms/suites/`), но работает на любом проекте, где кейсы живут в markdown.

- **«Ручной QA-отдел в одной команде `/new-feature`.»**
- **«От тикета до тест-кейсов — без ручного выписывания.»**
- **«ISTQB-обоснованные тест-кейсы, которые можно закоммитить.»**
- **«Тесты как код-ревью: спланировали, написали параллельно, прошли два круга ревью.»**

**Подзаголовок:**
> Kensa-QA берёт ссылку на Linear / Jira / Confluence / Notion / Figma (или просто вставленный текст), строит план покрытия, ждёт вашего одобрения и параллельно пишет 10–60 ручных тест-кейсов в формате вашего проекта.

## 3. Проблема, которую решаем

| Боль команды | Что обычно происходит | Что даёт Kensa-QA |
|---|---|---|
| Тест-кейсы пишутся вручную и долго | QA выписывает 30 кейсов по тикету полдня | План + кейсы за один прогон, параллельно несколькими «инженерами» |
| Спека поменялась — кейсы устарели | Руками искать, что задело изменение | `/update-feature` находит задетые кейсы по `source_id` и переписывает только их |
| Покрытие непрозрачно | «Кажется, покрыли» | Чек-лист покрытия + матрица трассировки требований → кейсы |
| Качество тест-базы плывёт | Дубли, висячие шаги, дрейф тегов | `/audit` + `/analyze-cases` — механический и смысловой аудит всей базы |
| Нет обоснования практики QA | «Почему так тестируем?» нечем ответить | Каждый навык цитирует главу и учебную цель **ISTQB CTFL v4.0.1** |
| Дефекты ловятся поздно | Баг в спеке всплывает на код-ревью | `/review-spec` — статическое ревью требования **до написания кода** |

## 4. Целевая аудитория

### Основная ЦА
- **Ручные QA-инженеры** — кто пишет тест-кейсы и хочет убрать рутину, оставив за собой решения.
- **QA / Test Leads** — кому нужно планирование покрытия, риск-анализ, тест-планы и контроль качества базы.
- **Небольшие команды без выделенного QA** — где тесты пишет разработчик или тимлид «по остаточному принципу».

### Вторичная ЦА
- **Команды на Kensa TMS** — кто уже хранит кейсы в markdown под `.tms/suites/` (нативный формат).
- **Регулируемые / аудируемые команды** — кому нужно обосновать QA-практику ссылкой на ISTQB-стандарт.
- **Джуны и переучивающиеся в QA** — каждый написанный кейс — рабочий пример учебной цели CTFL: учат ISTQB на практике.
- **Пользователи Claude Code и OpenAI Codex** — плагин ставится в оба движка из одного репозитория.

### Кому НЕ подойдёт (честно)
- Тем, кому нужен **автотест-раннер**: плагин **проектирует и описывает** тесты, но **не исполняет, не автоматизирует и не заменяет** test runner.
- Тем, у кого кейсы хранятся только в проприетарной TMS без экспорта в markdown.

## 5. Что делает

### Базовый цикл
- **📝 Author** — из ссылки на Linear / Jira / Confluence / Notion / Figma (или вставленного текста) → чек-лист + 10–60 файлов кейсов.
- **🔄 Update** — спека поменялась → находит задетые кейсы по источнику и переписывает только изменённое. Без ручной охоты.
- **🔎 Audit** — на больших сьютах: помечает устаревшие черновики, дубли, висячие шаги, дрейф тегов, пропавшие ссылки на источник. По умолчанию read-only.

### Сдвиг влево и интеллект по тест-базе (read-only аналитика)
Шесть команд, которые **не пишут кейсы**, а выдают один коммитируемый markdown-артефакт в `.tms/reports/`:

| Команда | Что делает |
|---|---|
| `/pull-context <ref>` | Собирает весь контент из источников + связанные кейсы в досье |
| `/review-spec <ref>` | Статическое ревью требования (ISO 20246) — находит дефекты **в самой спеке** до написания кейсов |
| `/risk-assess <ref>` | Реестр продуктовых рисков (вероятность × влияние → уровень → рекомендуемая глубина тестов) |
| `/test-plan <epic>` | Тест-план по ISTQB §5.1, со сборкой ранее сделанных артефактов риска / контекста |
| `/analyze-cases [scope]` | Смысловой глубокий аудит базы пачкой ревьюеров — противоречия, смысловые дубли, пробелы покрытия |
| `/traceability [--deep]` | Матрица требования → кейсы; `--deep` маппит каждый критерий приёмки на кейсы |

### Браузерный QA и Routines (v0.12)
- Агент управляет браузером через `kensa browser` (навигация, клики, ввод, скриншоты, проверки) — **браузером владеет Kensa**, агент только управляет им по CDP на loopback.
- **Routines** — переиспользуемые сценарии-промпты (`.tms/routines/RT-*.md`): smoke-тур, отправка формы, базовый визуальный диф. Запускаются командой `/run-routine`, коммитятся как обычный markdown.

### Адаптация схемы и Blueprints (v0.13)
- **`/adapt-schema`** — пришли с экспортом из другой TMS? Агент `schema-bootstrap-agent` читает пару ваших реальных кейсов и **аддитивно** подгоняет схему проекта под них (`kensa schema preview/apply`), затем `kensa adapt ready` передаёт управление импортёру. Принцип: **данные следуют за схемой, а не наоборот**; импорт полного экспорта делает детерминированный импортёр Kensa (Universal format), не ломая схему.
- **`/blueprint`** — нод-графовые автоматизации (`.tms/blueprints/BP-NNN.json`), исполняемые Rust-движком: exec/data-пины, ветвления, циклы, HTTP/скрипты и **первоклассная нода-агент**, запускающая `claude`/`codex` прямо внутри потока. Управление через `kensa blueprint new/list/show/validate/run`; перед запуском обязательная валидация, скрипт/агент-ноды под consent-гейтом.

## 6. Как это работает (4 шага)

1. **`test-lead-agent`** читает память проекта, тянет спеку через MCP и предлагает план покрытия.
2. **Вы одобряете план.** Human-gate — пока не подписали, ничего не запускается.
3. **`qa-engineer-agent`** работают параллельно. Каждый пишет свой срез в два этапа — сначала чек-лист, потом кейсы — с ревью тест-лида после каждого этапа (до 2 кругов правок на этап).
4. **На выходе:** новые/обновлённые `.md`-кейсы, чекпоинт памяти проекта и отчёт (файлы, пробелы, открытые вопросы).

Для стратегических решений («как разбить фичу?», «negative-first или boundary-first?») команда `/brainstorm` запускает трёх **стратегов** параллельно — они спорят и выдают 2–3 финалиста на выбор, а не пишут кейсы.

## 7. Ключевые дифференциаторы

1. **ISTQB CTFL v4.0.1 в основе.** 20 из 33 навыков цитируют главу, раздел и учебную цель ISTQB. Рассуждения **аудируемы** — можно показать регулятору, почему тестируем именно так.
2. **Не один промпт, а команда с ролями.** Тест-лид планирует и ревьюит, инженеры пишут параллельно, стратеги спорят. Два круга ревью на каждом этапе — как настоящее код-ревью для тестов.
3. **Human-gate по умолчанию.** Ничего не пишется, пока вы не одобрили план. Контроль остаётся за человеком.
4. **Память проекта в plain markdown/YAML.** Всё, что плагин учит про ваш проект, лежит в `.tms/` — читается, редактируется, коммитится. Никакого чёрного ящика.
5. **Покрывает QA-сторону всего SDLC** — от статического ревью спеки (shift-left) до интеллекта по всей тест-базе. Всё, кроме авторинга, — read-only.
6. **Два движка из одного репозитория** — Claude Code и OpenAI Codex. 33 навыка имеют единый дом и не расходятся между движками.
7. **Без API-ключей.** Linear / Jira / Confluence / Notion / Figma подключаются через браузерный OAuth при первом обращении.
8. **Браузерный QA встроен.** Routines дают исполняемые сценарии «открой → проверь → запиши результат обратно в кейс».

## 12. Установка (для CTA-блока)

Плагин собирается в **два чистых движка из одного монорепо** — отдельно для Claude Code и для OpenAI Codex. Готовые папки лежат под `dist/claude/` и `dist/codex/`, каждая самодостаточна (агенты, навыки, хуки, манифест внутри).

**Claude Code (в одну строку):**
```
/plugin marketplace add rpluzhnikov/QA_agents
/plugin install kensa-qa@rpluzhnikov
```

**OpenAI Codex (скопировать сборку в корень проекта):**
```
git clone https://github.com/rpluzhnikov/QA_agents.git
cp -R QA_agents/dist/codex/. /path/to/your-project/
```

**Через IDE:** редактор читает `engines.json`, показывает выбор движка и копирует нужную сборку в проект.

После установки — `/setup` (Claude) или `/kensa-setup` (Codex): бутстрап `.tms/memory/` и подключение MCP-источников.

## 13. Структура памяти проекта (для скриншота)

```
<your-project>/.tms/
├── memory/
│   ├── project.md         ← что за проект, стек, типы тестов
│   ├── conventions.md     ← как здесь пишутся кейсы
│   ├── glossary.md        ← доменные термины и переводы
│   ├── sot.yaml           ← конфиг источников правды
│   └── learned/           ← паттерны, общие шаги, теги (пишет плагин)
├── suites/                ← тест-кейсы по фичам
├── shared-steps/          ← переиспользуемые шаги
├── reports/               ← вывод /audit и аналитики
├── brainstorms/           ← вывод /brainstorm
├── routines/              ← браузерные routines RT-*.md
└── blueprints/            ← нод-графовые автоматизации BP-NNN.json
```

Всё — plain markdown/YAML. Читается, редактируется руками, коммитится в git.

## 15. Глоссарий терминов

- **TMS** — Test Management System. Здесь — формат [Kensa](https://kensa.dev): кейсы в plain markdown под `.tms/suites/`.
- **ISTQB CTFL v4.0.1** — Foundation Level сертификация по тестированию ПО; база, на которой обоснованы рассуждения плагина.
- **SOT (Source of Truth)** — источник требований: Linear, Jira, Confluence, Notion, Figma.
- **Human-gate** — точка, где плагин ждёт одобрения человека перед действием.
- **Routine** — переиспользуемый сценарий-промпт для браузерного QA.
- **Blueprint** — нод-графовая автоматизация с exec/data-пинами и агент-нодой.
- **MCP** — Model Context Protocol, через который агенты тянут спеки из трекеров.
