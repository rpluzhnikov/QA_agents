Kensa QA v0.5 (текущее состояние)

Мульти-агентный Claude Code плагин: команда мануального QA в кармане. Lead планирует и ревьюит, Worker пишет чек-листы и тест-кейсы, Strategist деберутует сложные стратегические вопросы. Это схема того, как сейчас всё устроено и куда что течёт.
Пользователь Lead агент Worker агент MCP / SOT Память проекта Артефакты (тест-кейсы)

1 · Slash-команды (точки входа)

Lead /setup
Один раз на проект. Интервью → создаёт .tms/memory/, пишет .mcp.json с SOT-серверами, учит конвенции из существующих кейсов.
Lead /new-feature <ref>
Главный сценарий. Тикет / URL / описание → Lead собирает контекст, планирует, делегирует Worker'ам, ревьюит, отчитывается.
Lead /update-feature <ref>
Фича изменилась. Lead ищет затронутые кейсы по source_id/тегам/глоссарию, решает update / delete / split / keep.
Lead /save-memory
Зафиксировать выученное за сессию в conventions.md / glossary.md / learned/*. Только с подтверждения юзера.
Lead /audit
Health-check репо: kensa-cli (validate, lint, duplicates, stale, orphans) + cross-reference с sot.yaml и taxonomy + sample против conventions. Отчёт в .tms/reports/audit-YYYY-MM-DD.md. Read-only по умолчанию; opt-in fixes в конце.
Lead /brainstorm <topic>
3 Strategist'а параллельно + cross-review раунд для сложных стратегических вопросов (декомпозиция, coverage strategy, prioritization). Synthesis с finalist'ами; user выбирает. Артефакт в .tms/brainstorms/ для следующего /new-feature.

2 · Главный pipeline — /new-feature

👤 Пользователь
Даёт ссылку на тикет / URL / описание
▼ план на ревью
Подтверждает план или правит scope
▼ финальный отчёт
Получает summary: файлы, кол-во, допущения, открытые вопросы
🧭 Lead — собрать контекст
1Распарсить ref (тикет ID / URL / free-text)
2Прочитать .tms/memory/*
3Через MCP вытянуть AC из SOT + найти соседние кейсы в .tms/suites/
🧭 Lead — план
4Скилл scope-analysis: in-scope, out-of-scope, декомпозиция
Решение: 1 worker (по умолчанию) или N параллельных, если поверхности независимы
Показать план юзеру → ждать «ок»
🛠 Worker — Stage 1: чек-лист
5Lead через Task спавнит worker'а с брифом: scope, ссылки, скиллы, suite path, stage: checklist
Worker применяет checklist-design + test-design-techniques + negative-and-edge-cases + платформенный скилл
Возвращает чек-лист Lead'у (юзер не видит)
🧭 Lead — ревью × 2
6Ревью чек-листа по review-rubrics: approved / approved with notes / send back (макс 2 круга)
🛠 Worker — Stage 2: кейсы
7Пишет .md кейсы в .tms/suites/<...> по kensa-test-authoring + test-case-writing-craft
8Ревью кейсов Lead'ом — те же 3 ответа, макс 2 круга
📁 Артефакты
.tms/suites/<area>/*.md — тест-кейсы со status: draft, generated_by: kensa-qa@0.5.0, source_id из тикета
Ссылки на shared steps из .tms/shared-steps/ вместо дублирования
🧠 Память (по согласию)
Новые паттерны → .tms/memory/learned/*

3 · Агенты и их инструменты

Lead agents/lead.md
Только Lead говорит с пользователем. Tools: Read, Glob, Grep, Bash, Task, mcp__* — НЕТ Write/Edit, он не пишет кейсы руками.

Скиллы, которые он триггерит сам: scope-analysis, review-rubrics, task-assignment, clarification-protocol, checklist-design, kensa-cli (включая /audit workflow), sequential-thinking.
Worker agents/worker.md
Спавнится Lead'ом через Task в /new-feature и /update-feature. С юзером не общается. Tools: Read, Write, Edit, Glob, Grep, mcp__* — пишет файлы.

Lead в брифе явно перечисляет ему скиллы: always — kensa-test-authoring, test-case-writing-craft, test-design-techniques, negative-and-edge-cases; одна платформа — web-testing / mobile-testing / backend-api-testing / security-testing; один SOT-скилл; опционально kensa-cli.
Strategist agents/strategist.md
Спавнится Lead'ом группами по 3 в /brainstorm. Tools: Read, Glob, Grep, mcp__* — БЕЗ Task, БЕЗ Bash. Не пишет кейсы, не запускает CLI.

Mission: аргументировать назначенную ось (Scope / Decomposition / Test strategy / Prioritization / Effort / Maintainability) как единственно правильный ответ. Synthesis — задача Lead'а. Round 1: independent proposal. Round 2: cross-review других двух пропозалов.

bundled sequential-thinking
Объявлен прямо в plugin.json, поднимается через npx @modelcontextprotocol/server-sequential-thinking. Без кредов. Питает скилл sequential-thinking.
внешние SOT — пишутся в .mcp.json репозитория командой /setup
Linear · SSE mcp.linear.app/sse · скилл sot-linear
Jira + Confluence · один atlassian сервер mcp.atlassian.com · скиллы sot-jira, sot-confluence
Notion · mcp.notion.com · скилл sot-notion
Figma (Dev Mode, read) · локальный 127.0.0.1:3845 · скиллы sot-figma, figma-use
OAuth в браузере на первом подключении. Если MCP не подключен — Lead честно говорит юзеру «запусти /setup или вставь текст».

6 · Что ложится на диск

memory .tms/memory/ — человекочитаемое, плагин перечитывает каждую сессию
.tms/memory/ ├── project.md ← что за проект, стек, типы тестирования (юзер) ├── conventions.md ← как пишутся кейсы (юзер, плагин читает) ├── glossary.md ← домен-термины (юзер) ├── sot.yaml ← конфиг источников правды └── learned/ ← пишется плагином, юзер ревьюит ├── patterns.md ├── shared-steps.md └── tags.md
MCP .mcp.json в корне репо
{ "mcpServers": { "linear": { … }, "atlassian": { … }, "notion": { … }, "figma": { … } } } // sequential-thinking // тут НЕ пишется — // он в plugin.json
output .tms/suites/ + .tms/shared-steps/
.tms/suites/<area>/ case-001.md case-002.md … # frontmatter каждого: # id, title, priority # status: draft # tags, source_id # generated_by: # kensa-qa@0.5.0 .tms/shared-steps/ step-XYZ.md

7 · Ключевые контракты, которые держат всё это

Двухстадийное ревью
Worker никогда не сдаёт сразу кейсы — сначала чек-лист, его Lead approves, и только потом Stage 2: cases. Каждый круг ревью капается на 2 итерации, дальше — эскалация юзеру.
Lead — единственный канал к юзеру
Worker не имеет тула спросить. Если у него гэп — пишет GAP: / ASSUMPTION: в выводе, Lead решает: подтвердить, переопределить или поднять юзеру.
Параллелизм по умолчанию выключен
Lead спавнит ОДНОГО Worker'а, если только нет явно независимых поверхностей (UI + API, web + mobile) или > 15 кейсов с чистым разделением. Параллелизм стоит токенов.
Память — только с согласия
Lead не дописывает learned/* молча. Либо предлагает каждый пункт и ждёт yes/no/edit, либо юзер заранее включил auto_save_learnings: true в project.md.
Стиль наследуется, не изобретается
Worker читает 3–5 существующих кейсов до того, как писать новые: phrasing заголовков, форма глаголов в шагах, формат expected results. Плохой стиль — не его проблема, это решение Lead'а.
Файлы → git-friendly
kensa-test-authoring описывает byte-exact формат: порядок ключей frontmatter, разметка шагов, ссылки на shared-steps, trailing newline — чтобы Kensa GUI не churn'ил файл при пересохранении и diff'ы оставались чистыми.
